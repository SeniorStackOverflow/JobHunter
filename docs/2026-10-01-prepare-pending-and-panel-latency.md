# Холостой CPU в `prepare_pending_applications` и медленная панель (2026-10-01)

Разбор алерта «JobHunter снова жрёт CPU впустую» и жалобы оператора на загрузку
страниц панели по 5–6 секунд. Расследование — только чтение PROD и изолированная
копия данных; исправления разработаны и проверены в DEV.

## Алерт реален

Логи `matching-worker` за три часа до исправления: задача выполнялась 23 раза,
в среднем **91,8 с** (максимум 118,7 с), в 21 случае из 23 результат 0. Расписание —
каждые 300 с, то есть около 30 % времени одно ядро было занято впустую.

## Причина 1: оценки профиля, который нельзя обрабатывать

В PROD два профиля: активный (8808 пар «профиль — вакансия», у каждой есть отклик)
и черновик другого аккаунта (5160 оценённых пар, ни одного отклика, последняя оценка
29 сентября). `prepare_pending_applications` выбирала последние оценки **всех**
профилей. Для каждой пары черновика вызывался `prepare()`, получал
`profile or account is not active`, выполнялся commit — и так каждые пять минут.
Замер на копии: 5160 из 5446 вызовов за цикл.

Исправление: выборка ограничена `ProfileService.list_processing_profiles` — тем же
правилом, по которому `prepare()` и matching допускают профиль. Если таких
профилей нет, задача выходит сразу.

## Причина 2: пары без итоговой записи перебирались вечно

Коммит `4f04db0` (добор минимума, PROD с 30 сентября) добавил в подготовку отбор
`require_employer_slot`: кандидат, который сейчас нельзя отправить автоматически
(не `auto_apply`/не ступень добора, занят слот работодателя, компания уже выбрана
сегодня), пропускался, и `prepare()` завершался ошибкой, не оставляя записи.
Последствия:

- существующий отклик не перепривязывался к более свежей оценке и перебирался
  каждый цикл: 277 откликов на копии (273 — после выкладки `4f04db0`), в том числе
  38 в очереди «Требуют решения» со старой оценкой;
- новая вакансия с оценкой `skip`/`prepare_for_review` или с занятым работодателем
  вообще не получала отклика: в PROD к 11:20 1 октября таких было уже 3, и с этого
  дня создавались только `auto_approved` отклики (раньше ежедневно появлялись
  `deferred`, `pending_review`, `skipped`);
- каждая такая попытка стоила около 95–136 мс (расчёт дневной цели, поиск
  контакта, проверка слота), а их число росло примерно на число новых вакансий
  в день.

Исправление: планировщик снова готовит каждую ожидающую пару без отбора по слоту.
Итог определяет `PolicyEngine`, который уже проверяет все условия удалённого
блока: слот работодателя и «одна компания в день» → `deferred`, подавление
работодателя и scam → `blocked`, порог оценки с учётом добора и обязательные
требования → `pending_review`/`skipped`. Порядок «лучший кандидат первым» сохраняет
сортировка по оценке. Автоотправка не ослаблена.

## Замеры задачи на копии PROD (pinned cycle)

| | Старый код | Новый, 1-й цикл | Новый, 2-й и 3-й циклы |
| --- | ---: | ---: | ---: |
| Время задачи | 89–104 с | 51 с | 12–14 с |
| Вызовов `prepare()` | 5446 | 286 | 5 |

Первый цикл разово обрабатывает накопившиеся отклики. Остаток в установившемся
режиме — плановая перепроверка правил для 100 откликов за цикл
(`application_policy_refresh_batch_size`), около 9 с.

Сверка итогов на двух одинаковых копиях: новый код **не одобрил к автоотправке ни
одного отклика**, как и старый. 282 отклика перепривязаны к свежей оценке, у 73
сменился статус: 29 `blocked` → `deferred`, 20 `pending_review` → `deferred`
(у работодателя уже есть активный отклик), 17 `deferred/pending_review` →
`deferred`, 5 `cancelled/skipped` → `deferred`, 2 `pending_review` → `cancelled`
(новая оценка `skip`).

## Медленные страницы

Замер в PROD: каждая вкладка `/admin` отдавалась за 5–7 с, `/admin/accounts` — за
0,1 с. На любой вкладке выполнялись:

| Операция | Время | Нужна |
| --- | ---: | --- |
| `daily_minimum_audit` — replay всей истории оценок профиля (8808 пар, полные строки с письмами и объяснениями) | 6,0 с | только блоку недобора на «Главной» |
| `count_profile_matching_backlog` — hash join по всей таблице оценок | 1,7 с | только тексту на «Главной» |
| последние события журнала — полное сканирование `audit_events` (500 тыс. строк, 212 МБ, без индекса) | 1,2 с | только «Главной» |

Исправления:

- диагностика минимума и backlog считаются только для «Главной»; остальным вкладкам
  для счётчика в шапке достаточно `daily_target_state`;
- полный replay запрашивается, лишь когда шаблон показывает разбор недобора
  (`include_replay`); в остальных случаях — живое состояние цели;
- replay читает кортежи нужных значений вместо ORM-сущностей; результат на копии
  PROD побайтно совпал с прежним для трёх срезов (текущий, 30.09, 01.10);
- в соединение запроса backlog добавлены условия, следующие из совпадения id
  (тот же профиль и та же вакансия): условие отбора не изменилось, план — 1,7 с →
  0,34 с; этот же запрос использует matching;
- индекс `ix_audit_events_timestamp` (миграция `c5d7a9e1f3b2`): 606 мс → 0,8 мс.

Замер на копии PROD (хост под нагрузкой):

| Страница | Было | Стало |
| --- | ---: | ---: |
| Вкладки «Требуют решения», «История», «Настройки», «Звонки» | 4,3–4,7 с | 0,2–0,5 с |
| «Главная», недобор (полный replay) | 4,7 с | 2,9 с |
| «Главная», минимум выполнен или автоотправка выключена | 4,7 с | без replay |
